What is Kubernetes?

Imagine you have a web app running inside a Docker container. Great — one container, one machine, it works. But now your app gets popular. One machine can't handle the traffic. What do you do?

You need to run many copies of your container across many machines — and something needs to manage all of them: restart crashed containers, spread traffic, roll out updates without downtime. That "something" is Kubernetes (often written as K8s).

Analogy

Docker is like a single chef cooking a dish. Kubernetes is the restaurant manager — scheduling chefs, handling rush hours, replacing anyone who calls in sick, and making sure every table gets served.

Kubernetes was originally built at Google, open-sourced in 2014, and is now maintained by the CNCF (Cloud Native Computing Foundation). Every major cloud provider — AWS, GCP, Azure — has a managed Kubernetes service.

Orchestration
Automating deployment, scaling, and management of containers
K8s
Shorthand for Kubernetes (8 letters between K and s)
CNCF
Cloud Native Computing Foundation — the open-source home of K8s

Docker brush-up — containers & images

Before Kubernetes makes sense, you need a mental model of what it's actually managing: containers.

The problem containers solve

Classic problem: "It works on my machine." Your app runs fine locally, breaks in production because the server has a different Python version, different OS libraries, different everything. Containers fix this by bundling your app and everything it needs into one portable unit.

Analogy

A container is like a shipping container — standardized, self-contained, works on any ship (server), any port (cloud). The contents don't care where they end up.

Images vs. containers

Image
A read-only blueprint/template. Like a class in OOP. Defined in a Dockerfile.
Container
A running instance of an image. Like an object created from a class. Has its own filesystem and process.
Dockerfile
A script of instructions to build an image — what OS, what dependencies, what code to run.
Registry
A store for images. Docker Hub is the public one. Think of it like GitHub but for container images.

Key Docker commands (for reference)

# Pull an image from Docker Hub docker pull nginx # Run a container from an image docker run -d -p 8080:80 nginx # List running containers docker ps # Stop a container docker stop <container-id> # Build an image from a Dockerfile docker build -t my-app:1.0 .

Where Docker ends and Kubernetes begins

Docker is great for running containers on one machine. But it has no built-in way to:

✗Automatically restart a crashed container on a different machine
✗Spread containers across 10 servers and balance traffic between them
✗Roll out a new version of your app with zero downtime

This is exactly what Kubernetes was built for. You describe what you want — "run 5 copies of my app, always" — and Kubernetes makes it happen and keeps it that way.

Key insight: Kubernetes doesn't replace Docker. It uses Docker (or another container runtime) under the hood — it just manages containers at scale.
1

Create a Kubernetes cluster

A cluster is the foundation of Kubernetes — a group of machines (physical or virtual) that work together to run your containers.

Anatomy of a cluster

Control Plane (Master)
The brain. Decides what runs where, monitors health, handles API requests. You don't run your app here.
Worker Node
The muscle. Actual machines that run your containers. A cluster can have 1 to thousands of nodes.
kube-apiserver
The front door to the control plane. Every command you run goes through it.
etcd
Kubernetes' database. Stores all cluster state — what's running, what's supposed to run.
kubelet
An agent running on every worker node. Ensures containers are running as instructed.
kubectl
Your command-line tool to talk to the cluster. Pronounced "kube-control" or "kube-c-t-l".

Minikube — a cluster on your laptop

For learning, we use minikube, which spins up a single-node Kubernetes cluster locally inside a VM or container. It gives you a real Kubernetes environment without needing cloud infrastructure.

# Start a local cluster minikube start # Check cluster info kubectl cluster-info # See the nodes in your cluster kubectl get nodes
Expected output of "kubectl get nodes": one node named "minikube" with status "Ready".
Mental model

Think of the control plane as the HR/management team, and worker nodes as employees. HR decides who does what; employees do the actual work. kubectl is your phone call to HR.

Deploy an app

Now that you have a cluster, it's time to run something on it. You do this by creating a Deployment.

Key concepts

Pod
The smallest unit in Kubernetes. A pod wraps one (or more) containers and runs on a node. Think of it as one running instance of your app.
Deployment
A higher-level object that manages pods. You tell it "I want 3 copies of this pod" and it creates, monitors, and restarts them.
ReplicaSet
What the Deployment creates behind the scenes to maintain the right number of pod copies. You rarely touch this directly.
Analogy

A Pod is one waiter in a restaurant. A Deployment is the manager who says "we always need 3 waiters on the floor — if one quits, hire another immediately."

Deploying with kubectl

# Deploy an app using a public image kubectl create deployment hello-node \ --image=registry.k8s.io/e2e-test-images/agnhost:2.39 \ -- /agnhost netexec --http-port=8080 # See the deployment kubectl get deployments # See the pods it created kubectl get pods

What happens behind the scenes

1You run kubectl create deployment — this sends a request to the API server.
2The control plane stores the desired state in etcd: "1 pod, this image".
3The scheduler picks a worker node that has available resources.
4The kubelet on that node pulls the image and starts the container.
5The pod appears as "Running". Kubernetes will keep it running forever — if it crashes, it restarts automatically.
Self-healing in action: kill a pod manually with "kubectl delete pod <name>" — a new one appears within seconds because the Deployment says "I need 1 pod".

Explore your app

Your app is running — but how do you see what's happening inside? Kubernetes gives you several inspection tools.

Inspecting pods and deployments

# List all pods with extra details (node, IP, age) kubectl get pods -o wide # Deep-dive into one pod — events, status, container info kubectl describe pod <pod-name> # Read the logs from inside a pod (like docker logs) kubectl logs <pod-name> # Open an interactive shell inside a running pod kubectl exec -it <pod-name> -- /bin/bash # Forward a pod port to your local machine (quick local access) kubectl port-forward <pod-name> 8080:8080

Reading kubectl describe output

The describe command is your best debugging friend. Key things to look at:

Events section
Shows what Kubernetes did recently — pulled image, scheduled, started, or any errors.
State
Running, Waiting, or Terminated. "Waiting" with a reason tells you what's wrong.
Restart Count
If this is non-zero, your container is crashing and restarting — called a "CrashLoopBackOff".
Conditions
Ready, PodScheduled, ContainersReady — all should be True for a healthy pod.
Port-forwarding is great for testing. It creates a temporary tunnel from your laptop to the pod — no need to expose it publicly yet.

Expose your app publicly

By default, pods are only reachable within the cluster — they have an internal IP that no one outside can hit. To make your app accessible, you create a Service.

Analogy

A Service is like a receptionist at a company — callers don't need to know which specific employee (pod) will handle their request. They just call the front desk (the Service), and the receptionist routes them.

Types of Services

ClusterIP (default)
Accessible only inside the cluster. Good for internal communication between services (e.g., app → database).
NodePort
Exposes the service on each node's IP at a static port (30000–32767). Reachable from outside the cluster.
LoadBalancer
Provisions an external load balancer (from your cloud provider). The "production-ready" way to expose apps.
Ingress
Not a Service type, but a smart router that maps URLs/paths to Services. Used for routing multiple apps at once.

Exposing with kubectl

# Expose a deployment as a NodePort service kubectl expose deployment hello-node \ --type=NodePort \ --port=8080 # List services kubectl get services # In minikube, open the service in a browser minikube service hello-node
Services use label selectors to find pods — not names or IPs. This is why you can delete and recreate pods and the Service still routes to them correctly.

Scale your app

One of Kubernetes' core powers is the ability to run multiple identical copies of your app — called replicas — and balance traffic across all of them.

Scaling manually

# Scale up to 4 replicas kubectl scale deployment hello-node --replicas=4 # Watch the pods appear in real time kubectl get pods -w # Scale back down kubectl scale deployment hello-node --replicas=2

When you scale to 4 replicas, Kubernetes creates 3 new pods. Your Service automatically routes incoming requests across all 4 pods using round-robin load balancing — no extra config needed.

Autoscaling (HPA)

Manually scaling is fine for demos — in production you'd use a Horizontal Pod Autoscaler (HPA), which watches CPU/memory and scales automatically.

# Auto-scale between 2 and 10 replicas based on CPU kubectl autoscale deployment hello-node \ --cpu-percent=50 \ --min=2 \ --max=10
Horizontal scaling
Add more copies of the pod. Best for stateless apps. This is what Kubernetes does natively.
Vertical scaling
Give the pod more CPU/RAM. Requires a restart. K8s has a VPA for this, but it's less common.
Scaling only works well for stateless apps — where any pod can handle any request. If your app stores session data in memory, users might hit different pods and lose their session.

Update your app

Updating an app in production is risky — you don't want downtime while the old version shuts down and the new one starts. Kubernetes solves this with rolling updates.

How rolling updates work

1You update the image in the Deployment to the new version.
2Kubernetes creates one new pod with the new version.
3Once the new pod is healthy ("Ready"), it terminates one old pod.
4This repeats until all old pods are replaced. Traffic is always being served.

By default, Kubernetes ensures at least 75% of pods are available at all times during an update. At no point is your app completely down.

Updating and rolling back

# Update the image to a new version kubectl set image deployment/hello-node \ hello-node=<new-image:version> # Watch the rollout happen kubectl rollout status deployment/hello-node # See rollout history kubectl rollout history deployment/hello-node # Something went wrong? Roll back instantly kubectl rollout undo deployment/hello-node

Update strategies

RollingUpdate (default)
Gradually replaces old pods with new ones. Zero downtime. The right choice for most apps.
Recreate
Kills all old pods first, then creates new ones. Has downtime. Only use if old and new versions can't run at the same time.
maxSurge
How many extra pods can exist above the desired count during an update. Default: 25%.
maxUnavailable
How many pods can be offline during an update. Default: 25%.
Rollbacks are instant — Kubernetes remembers previous ReplicaSets. "kubectl rollout undo" switches traffic back in seconds, not minutes.
